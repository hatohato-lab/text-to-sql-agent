# text-to-sql-agent 設計メモ

この文書は「なぜこの設計にしたか」の記録。使い方は README を参照。

## 実証する設計パターン
**実行（execution）オラクル**。出力（SQL）の正解が一意に決まらない場合に、出力の文字列ではなく
**実際に実行した結果**を基準と突き合わせて合否を決める。

## なぜこの方式を選んだか（他方式との比較）★この repo の肝
- 同じ意味の SQL は何通りも書ける（別名・順序・書式が違っても正しい）。だから文字列一致（golden）は使えない。
- 一方、SQL の「正しさ」は実行結果で決まる。お手本SQLと候補SQLを同じDBで動かし、結果集合が一致するかで判定できる。
- 順序を無視した集合として比べるので、ORDER 指定の無い問いでも書式差に強い。
- 対比：差分テスト＝元プログラムの出力を基準。仕様アサーション＝出力が満たす条件を検証。本 repo は「**出力が一意でない＋実行すれば結果で白黒つく**」列（実行オラクル）を担当。

## 判定の手順
1. 固定のDB（社員テーブル）を毎回ゼロから作る。
2. お手本SQLと候補SQLをそれぞれ実行し、結果を順序非依存で比較する。
3. 候補が実行エラーなら不合格。

## なぜ信頼できるか（オラクル自己検証）
`--selftest` で、正しいSQL集は PASS、既知バグ（部署の取り違え／WHEREの欠落＝結果が違う、文法エラー＝実行不可）は FAIL になることを示す。

## 既知の限界
- 判定はこのテストDB・このお題に対するもの。別データや別問では別途お題と基準が要る。
- 結果が同じなら非効率なSQLも通る（正しさのみ・性能は別オラクルの担当）。
- 比較は「行タプルの文字列一致」なので、列の並び順・値の型（整数/実数など）に感度がある。意味が同じでも列順が違えば FAIL になる（例: q3 で `AVG(salary), dept` の順に出すと不一致）。
- q4（最高給与の人）は、最高給与が同点で複数いるデータでは `LIMIT 1` 方式と `MAX` 副問い合わせ方式で結果が割れうる。単一シードDB（現状は同点なし）に依存した判定であり、同点時の仕様は未定義。
- オラクルは候補ファイルを Python として import 実行し、SQL も無検証で実行する。信頼できる候補コードのみを採点対象とする前提（ローカル採点用であり、未知のコードのサンドボックスではない）。
